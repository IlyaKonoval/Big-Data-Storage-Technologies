# Краткое резюме  
Проект организует **ETL-пайплайн** для сбора, хранения и анализа орбитальных элементов искусственных спутников Земли с использованием данных CelesTrak. Используются CelesTrak GP/SupGP‑источники (TLE и более точные данные), хранилище ODS для сырых данных и нормализованный DDS (dim/fact). План включает три Airflow DAG (разные группы спутников), стратегии загрузки (initial load и инкремент), правила качества данных, SQL‑upsert и набор визуализаций в Superset. Учитываются ограничения CelesTrak (лимиты запросов, политика обновлений).

## Цели и задачи  
- **Сбор данных:** периодическая выгрузка орбитальных элементов (TLE/GP) и доп. данных (SupGP) с CelesTrak (бесплатный источник данных о спутниках).  
- **Хранение данных:** формирование ODS-хранилища (сырые JSON/CSV) и переход к нормализованной 3НФ/DDS схеме (сателлит, орбита и т.д.).  
- **Анализ:** обеспечение витрин и дашбордов (Superset) для визуализации числа спутников, распределения орбит, трендов по запускам и жизненному циклу.  
- **Автоматизация:** три Airflow DAG-а для разных потоков данных (см. ниже), каждые DAG настраивается по расписанию (cron) и выполняет загрузку → ODS → преобразование → DDS.  
- **Качество и SLA:** контроль полноты и актуальности (время обновления ~2 ч), проверка корректности полей, мониторинг лимитов CelesTrak.

## Источники данных  
Все данные берутся из CelesTrak (официальный сайт Dr. T.S. Kelso). Основные разделы:  

- **GP (General Perturbations):** традиционные TLE-данные для **всех активных спутников**. Доступны в разных форматах (TLE, OMM, JSON, CSV). Обновляются обычно раз в ~2–3 ч. Пример API-запроса:  
  - `https://celestrak.org/NORAD/elements/gp.php?GROUP=GPS-OPS&FORMAT=CSV` – список GPS-спутников.  
  - `https://celestrak.org/NORAD/elements/gp.php?INTDES=2020-025&FORMAT=JSON-PRETTY` – орбиты спутников последнего запуска Starlink 2020-025.  

- **SupGP (Supplemental GP):** данные от операторов констелляций (напр. Starlink, OneWeb и др.), построенные на публичных эфемеридах. Позволяет получать точные элемент sets по категориям (например, Starlink в SupGP содержит сотни спутников).  

- **Ограничения:** официальный CelesTrak рекомендует не скачивать одни и те же наборы чаще, чем обновляются. Введены лимиты: **10 запросов в сутки (GP+SupGP вместе)**, макс **100 объектов в запросе**, не более **20 000 записей** за запрос. Кроме того, для групп `active` и `Starlink` действует политика “одно скачивание на обновление” – вторые запросы сразу вернут 403, пока данные не обновятся (≈2 ч). Также с июля 2026 г. в TLE-формате появились ограничения на 6-значные номера (используйте JSON/OMM).

## Схема данных (ODS/DDS и ключи)  

**ODS:** каждому DAG соответствует таблица-стадия (например, `ods_gp_active`, `ods_gnss`, `ods_starlink`) со столбцами JSON/структурированными из запросов. Ключи – произвольные UUID или timestamp, уникальность не требуется.  

**DDS (пример 3НФ):**  
- `dim_satellite`: *sat_id* (PK, NORAD Catalog N), `name`, `classification_type`, `launch_group` (Starlink/GP), `effective_from`, `effective_to`, `is_current`. (SCD Type2: если имя или статус спутника меняется, старой записи ставится `effective_to`, `is_current`=False).  
- `fact_orbit`: PK – суррогатный или композит `(sat_id, epoch)`; FK *sat_id*→dim_satellite; поля: `epoch`, `inclination`, `raan`, `eccentricity`, `arg_of_perigee`, `mean_anomaly`, `mean_motion`, `bstar`, `revision`.  
- (При необходимости: `dim_group`/`dim_agency`, `dim_launch` – информацию о констелляции и пуске спутника; наполнение по SATCAT или другим источникам).  

**Связи и ключи:**  
`dim_satellite.sat_id` – суррогатный ключ (а также фактически NORAD_CAT_ID), PK.  
`fact_orbit.sat_id` – внешний ключ на dim_satellite.  
`fact_orbit.epoch` – точка времени измерения, уникальная в сочетании с sat_id.  

*Пример соответствия полей API → таблицам:*  

| Сущность           | Поля из API (GP/SupGP)                                | Целевая таблица     |
|--------------------|-------------------------------------------------------|---------------------|
| Спутник (объект)   | `NORAD_CAT_ID` (sat_id), `OBJECT_NAME`, `CLASSIFICATION_TYPE` | `dim_satellite`     |
| Орбитальное измерение | `NORAD_CAT_ID`, `EPOCH`, `INCLINATION`, `RA_OF_ASC_NODE`, `ECCENTRICITY`, `ARG_OF_PERICENTER`, `MEAN_ANOMALY`, `MEAN_MOTION`, `BSTAR` | `fact_orbit`        |
| **(фактическая таблица)** | | **(Destination)**         |
| (текущий статус данных) | время обновления, источник данных                     | Метаданные загрузки (неявно) |

## Airflow DAG и расписание  

Три отдельных DAG с разными группами данных: 

| DAG             | Источник (API, параметр)                               | Schedule             |
|-----------------|--------------------------------------------------------|----------------------|
| **GP Active**   | `GP`-запрос CelesTrak: `GROUP=active`, `FORMAT=JSON` (или CSV) | `*/120 * * * *` (каждые 2 часа)   |
| **GPS/GLONASS** | `GP`-запросы: `GROUP=GPS-OPS`, `GROUP=GLONASS-OPS`, `FORMAT=CSV` | `0 0 * * *` (ежедневно в полночь) |
| **Starlink**    | `SupGP`-запрос CelesTrak: специализированный GP (или SupGP) для Starlink, например `TABLE&FILE=starlink` или gp.php с фильтром; см. официальные инструменты SupGP | `0 */6 * * *` (каждые 6 часов)    |

Каждый DAG выполняет: HTTP GET к CelesTrak, сохраняет JSON/CSV в ODS (стажинговую таблицу), затем запускает SQL-скрипты для upsert в DDS. Примеры запросов можно сделать через `requests`/`curl` (см. примеры ниже).

## Initial load и инкрементальная загрузка  

- **Initial load:** при первом запуске выполняется полный сбор данных для выбранных групп (GP-active, GPS, Starlink). Из-за ограничений CelesTrak (10 req/сутки) initial load следует разбить на несколько дней или использовать разделение по группам. Например, сначала запросить GPS/GLONASS, затем Starlink, затем Active. Если данных много, можно запрашивать порционно (GP active можно разбить по диапазонам Catalog№).  

- **Инкремент:** после initial load каждый DAG забирает **только новые или изменённые записи**. Для GP-данных сложно использовать метки изменений, поэтому стратегия: всегда загружать свежий снимок и выполнять UPSERT (INSERT … ON CONFLICT DO UPDATE) в таблицу фактов. Для новых спутников в `dim_satellite` – SCD2: если спутник уже есть и данные не изменились – пропустить, иначе закрыть старую запись (`effective_to`) и вставить новую.  

- **SCD Type 2:** например, если меняется принадлежность или статус спутника, в `dim_satellite` старая запись помечается неактуальной, и создаётся новая с `effective_from=now`.

| Источник данных      | Интервал | Строк/запрос | Строк в день       | Строк в неделю     | Строк в месяц      |
|----------------------|----------|--------------|--------------------|--------------------|--------------------|
| GP Active (все LEO)  | каждые 2 ч | ≈10 000     | ~120 000 (12×)     | ~840 000           | ~3,600 000         |
| GPS+GLONASS (GNSS)   | раз/сутки | ≈55        | ~55               | ~385               | ~1,650             |
| Starlink (SupGP)     | каждые 6 ч | ≈5 000      | ~20 000 (4×)      | ~140 000           | ~600 000           |

*Примечания:* Оценки основаны на текущих размерах групп (≈10k активных, ~5k Starlink). GP-данные обновляются ~каждые 2 ч, SupGP Starlink – можно забирать реже (например, 4 раза в сутки). Таким образом за месяц может накопиться несколько миллионов записей fact_orbit.  

## Правила качества данных (Data Quality)  
- **Полнота и уникальность:** `fact_orbit.sat_id` и `epoch` не должны быть NULL; комбинация `(sat_id, epoch)` уникальна (первичный ключ).  
- **Диапазоны значений:** `inclination` ∈ [0,180], `eccentricity` ∈ [0,1), `mean_motion` > 0. Если находятся вне диапазона – ошибка данных.  
- **Ссылочная целостность:** для каждой записи факта должно существовать соответствующее `sat_id` в `dim_satellite`.  
- **Точность времени:** `EPOCH` в ISO-формате, периодические обновления не реже одного раза в 2–3 часа (без пропусков более 24 ч для активных спутников).  
- **Статус актуальности:** новые записи двигают границы SCD (old record → `is_current=FALSE`).  
- **Логические проверки:** например, если `classification_type = U` (военный спутник) – имя или оператор не должен быть пуст; `mean_motion` и другие параметры должны корректно соответствовать заданному типу орбиты (лунная миссия – нет).  
- **Политика обновлений:** не нарушать лимиты CelesTrak – более одного запроса на группу `active`/`Starlink` за 2 часа приведёт к 403.  

## Пример SQL (Insert/Upsert)  

```sql
-- Вставка/обновление спутника (SCD2 пример):
INSERT INTO dim_satellite(sat_id, name, class, effective_from, is_current)
VALUES (25544, 'ISS (ZARYA)', 'U', NOW(), TRUE)
ON CONFLICT (sat_id) DO UPDATE
  SET name = EXCLUDED.name
  -- при изменении атрибута закрываем старую запись:
  , effective_to = CASE WHEN dim_satellite.name <> EXCLUDED.name
                        THEN NOW() ELSE dim_satellite.effective_to END
  , is_current = CASE WHEN dim_satellite.name = EXCLUDED.name THEN TRUE ELSE FALSE END;

-- Вставка данных орбиты:
INSERT INTO fact_orbit(sat_id, epoch, inclination, raan, eccentricity, arg_of_perigee, mean_anomaly, mean_motion, bstar)
VALUES (25544, '2026-10-16T18:00:00', 51.64, 257.11, 0.0007336, 130.536, 325.028, 15.72125391, 0.00002138)
ON CONFLICT (sat_id, epoch) DO NOTHING;
```

(В Airflow скриптах эти запросы запускаются после загрузки сырых данных из ODS.)  

## Визуализации в Superset  
Возможные метрики и дашборды:  
1. **Число спутников по типу орбиты:** бар-чарт или пирог (LEO/MEO/GEO, навигация, связь и т.д.), выводится из `dim_satellite`.  
2. **Динамика числа спутников во времени:** линейный график – сколько спутников было на орбите (итого/по констелляциям) на каждую дату (по `fact_orbit`).  
3. **Запуски по годам:** счётчики запусков (можно вывести через фильтрацию по `INT_DESIGNATOR`, либо через внешний `satcat`); сравнение Starlink vs другие.  
4. **Распределение орбитальных элементов:** scatter plot/inclination vs eccentricity или гистограммы `inclination`, `eccentricity`, `mean_motion`.  
5. **Гистограмма параметра BSTAR (сопротивление атмосферы):** выявляет убывающие или нестабильные спутники (см. примеры использования SORT+BSTAR).  
6. **Топ-10 операторов/целевых групп:** бар-чарт по числу спутников на разных орбитах (напр. Starlink, GPS, GLONASS, OneWeb).  
7. **Оповещательный виджет:** время последнего обновления GP-данных и объём загруженных строк.  
   
*Пример дашборда:* сводка по всём спутникам (карточка со скоростными метриками, график прироста спутников по годам, карта-список (Scatter Map) орбит или 3D-сцена, гистограммы BSTAR и распределения по группам).  

## Инфраструктура и ресурсы  
- **База данных:** реляционная СУБД (PostgreSQL/MySQL) для ODS и DDS. При объёмах ~10⁶ строк достаточно машины с 4–8 CPU, 8–16 GB RAM и ~10 GB диска. Для больших объёмов (млн+ строк) можно использовать колоночное хранилище (ClickHouse) для фактов аналитики.  
- **Хранилище сырых данных:** при необходимости – blob-хранилище (S3/GCS) или файловая система для JSON/CSV.  
- **Airflow:** сервер Airflow (Linux VM или Docker) для запуска DAG. Мелкая нагрузка – достаточно 1–2 ядра, 4 GB RAM.  
- **BI (Superset):** веб-интерфейс на отдельном узле или Docker-контейнере (минимум 2 CPU, 4 GB RAM).  
- **Сеть:** доступ в интернет к CelesTrak для загрузки.  
- **Хранение:** несколько гигабайт для исторических орбиталок (~10 млн записей ≈ 1–2 GB).  

## Ограничения CelesTrak  
- **Лимит запросов:** не более **10 запросов/сутки** по API GP/SupGP. Один запрос включает до 100 НО, максимум 20 000 записей. Крупные констелляции (Starlink) требуют либо многофазной загрузки, либо использования Space-Track.  
- **Частота обновлений:** GP-данные доступны ≈каждые 2 ч. Для групп `active` и `Starlink` CelesTrak жёстко запрещает повторные запросы до обновления (после 1-го успешного запроса следующий вернёт 403 «not updated»). Необходимо выжидать период обновления (~2 ч) и не дублировать запросы.  
- **Форматы:** с июля 2026 г. новые спутники получили 6-значные номера, недоступные в двухстрочном формате. Рекомендуется использовать JSON/OMM форматы.  
- **Политика:** при превышении лимитов (частое скачивание больших наборов) возможна блокировка IP (см. «Usage Policy»).  

## Тестирование  
- **Unit-тесты:** имитация запросов к CelesTrak с помощью заглушек (Mock API) и проверка обработки JSON в Pandas/Spark.  
- **Интеграционное тестирование:** запуск каждого DAG на ограниченном сете (например, групп спутников до 10 000) и сравнение количества записей с ожидаемыми.  
- **Тесты качества:** проверка, что правила DQ отрабатывают – например, вставлять тестовые «неправильные» записи и убедиться в ошибке.  
- **Нагрузочное тестирование:** имитация пиковой нагрузки (несколько DAG подряд) и контроль потребления ресурсов.  
- **Мониторинг:** настройка Airflow Alerts (в случае падения DAG) и логирование успешных загрузок/ошибок.  

**Источники:** официальная документация CelesTrak, включая «A New Way to Obtain GP Data», формы запросов и страницы Usage Policy.
